# 产品决策记录

## 渐进路线: A → B

先做豆瓣+闲鱼（方案A），验证产品价值，再扩展到 Firecrawl Search 全网搜索（方案B）。

**Why:** 降低 MVP 复杂度，先跑通核心流程。全覆盖在 side project 阶段不可行。

## 仅杭州

MVP 只做杭州，不展开全国。

**Why:** 单城市验证足够。多城市会增加爬取量、geocode 复杂度，且每个城市豆瓣小组结构不同。

## 联系信息公开

不脱敏。原文展示房东/转租人留下的微信、手机号。

**Why:** 联系方式是房东自己在公开平台发布的，聚合展示性质等同搜索引擎。脱敏会砍掉产品核心价值。

## 租赁方式与房东类型分开

两个独立维度，可以组合筛选。

**租赁方式:** 整租 / 合租 / 单间 / 转租 / 不限
**房东类型:** 个人房东 / 仅看转租 / 不限

**Why:** 转租是租赁方式的一种场景，个人/中介是房东身份。两者不互斥，分开能支持交叉组合（如"个人房东+整租"）。

## 中介识别

基于 5 个维度综合判定：同账号多房源(≥3)、中介话术、品牌名命中、发帖频率、联系方式重复。

标记 🟢个人 / 🔴中介 / ⚪信息不足。用户可过滤。

## 排序: 综合/最新/价格/距离

- 综合排序加权: 信息完整度 + 新鲜度 + 关键词匹配 + 来源可信度
- 距离排序需高德 geocode + 用户指定参考点

## 订阅通知: 邮件优先

每 2 小时扫描匹配，邮件推送摘要。微信通知需服务号认证，阶段 B 再考虑。

## 高德地图接入

用于地址→坐标转换 + 前端地图展示 + 距离计算。免费额度 5000次/天，远超 MVP 用量。
