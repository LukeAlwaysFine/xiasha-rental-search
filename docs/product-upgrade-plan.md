# 租房聚合平台 — 产品升级方案

## 一、当前产品诊断

管线扎实，产品薄弱。现有代码的抓取→提取→geocode→检测管线是及格的，但从产品视角看，它是一个"能用的搜索框"，不是"帮用户找到家的工具"。

| 维度 | 现状 | 问题 |
|------|------|------|
| 交互模式 | 关键词搜索 | 用户不知道搜什么。租房决策是**持续浏览+比较**，不是一次搜索。 |
| 地图 | 侧边栏配件 | 租房天然是地图优先的——用户先锚定通勤圈，再看房源。地图不该是配角。 |
| 房源理解 | 结构化字段 | 用户看到的是 price=2800, house_type=一居，但想知道的是"这房子值不值、安不安全、离公司远不远"。 |
| 平台覆盖 | 豆瓣+闲鱼 | 两个源不够。杭州每天新出租帖远不止这些。 |
| 用户粘性 | 零 | 搜完就走，没有收藏、提醒、历史。租房是高频重复行为，每天都该来看。 |
| LLM 使用 | 提取+去重 | LLM 能做更多：质量打分、骗局识别、自然语言搜索、区域洞察。 |

## 二、产品定位升级

```
现在：房源搜索引擎（搜 → 看 → 走）
升级：AI 租房助手（发现 → 理解 → 决策 → 提醒）
```

一句话：**让用户在 5 分钟内判断一套房值不值得联系房东，而不是花 30 分钟翻帖对比。**

## 三、核心功能设计

### 3.1 地图优先浏览（阶段 1，2-3 天）

**当前**：用户输入关键词 → 看列表 → 地图被动显示标记。

**改为**：进来就是杭州地图，拖动地图自动刷新当前视野内的房源。列表跟随地图。

```
┌─────────────────────────────────────────────────┐
│  🔍 [自然语言搜索: "西溪阿里附近 整租一居 2500"]  │
├────────────────────┬────────────────────────────┤
│  房源卡片（滚动）    │                            │
│  ┌──────────────┐  │       高德地图              │
│  │ ¥2200 一居    │  │    📍 📍                  │
│  │ 西溪北苑 45㎡  │  │      📍 📍 📍             │
│  │ ⭐质量分 8.2  │  │    📍   📍                │
│  │ 🟢个人 2h前   │  │                            │
│  ├──────────────┤  │  拖动地图 → 列表自动刷新     │
│  │ ¥2800 两居    │  │                            │
│  │ ...           │  │                            │
│  └──────────────┘  │                            │
├────────────────────┴────────────────────────────┤
│  共 156 套 · 当前区域均价 ¥2,450 · 比上周 ↓3%    │
└─────────────────────────────────────────────────┘
```

关键交互：
- 拖动/缩放地图 → `bounds` 参数传给 API → 返回视野内房源
- 侧边卡片点击 → 地图聚焦 + 弹出信息窗
- 底部状态栏展示"当前视野均价"，LLM 生成

**粘合现有代码**：API 已有 `lng/lat` 索引。新增 `/api/search` 参数 `sw_lng/sw_lat/ne_lng/ne_lat`，SQL 加 `WHERE lng BETWEEN ? AND ? AND lat BETWEEN ? AND ?`。前端监听 `map.on('moveend')` 触发搜索。

### 3.2 房源质量评分（阶段 1，1-2 天）

用户打开 30 条结果，真正值得联系的只有 5 条。LLM 帮助识别。

**评分维度（LLM 一次调用完成）**：

| 维度 | 权重 | 说明 |
|------|:----:|------|
| 信息完整度 | 20% | 有价格+面积+户型+地址+图片 |
| 真实性信号 | 25% | 个人转租理由具体、有实拍图暗示、价格在区域正常范围内 |
| 骗局风险 | 25% | 价格异常低、图片疑似网图、话术夸张、联系方式多平台出现 |
| 描述质量 | 15% | 帖子写得认真（不是"加微信详聊"一笔带过） |
| 时效性 | 15% | 新鲜发布加分 |

前端展示为 `⭐8.2分`，点击展开看到"为什么这个分数"。

**粘合现有代码**：`src/filter/` 下新增 `llm_quality.py`，在 `rerank_listings` 之后、`merge_duplicates` 之前调用。复用已有的 `AsyncOpenAI` + `extra_body={"thinking": {"type": "disabled"}}` 模式。

### 3.3 自然语言搜索（阶段 1，1 天）

**当前**：关键词 LIKE 匹配 title/address。

**改为**：用户在搜索框输入自然语言，LLM 解析为结构化过滤条件 + 地理坐标。

```
输入: "阿里西溪园区附近 整租一居 2500以内"
  ↓ LLM 解析
输出: {
  location: "阿里巴巴西溪园区",  → geocode → lng/lat + 半径
  rent_type: "整租",
  house_type: "一居",
  price_max: 2500,
  radius: 3000  // 默认3km
}
```

**粘合现有代码**：新增 `src/filter/llm_parse_query.py`，在 `/api/search` 入口处，如果 keyword 包含非地名关键词（用简单规则判断），先调 LLM 解析再搜索。LLM 调用极轻量（<100 tokens），成本可忽略。

### 3.4 智能收藏 + 新货提醒（阶段 2，3-5 天）

租房不是一锤子买卖。用户设置条件后，系统每 2 小时扫描新入库房源，匹配则推送。

```
用户设置: "西溪+未来科技城 整租一居 ≤2500"
     ↓
每 2h 新入库房源 → 匹配条件 → 匹配到 3 条新发布
     ↓
邮件推送（阶段 A）/ 微信通知（阶段 B）
```

**粘合现有代码**：`listings` 数据库加 `saved_searches` 和 `user_alerts` 表（SQLite，简单 schema）。定时任务 `scheduled_fetch()` 后追加 `check_alerts()`。邮件用 stdlib `smtplib`。前端加"🔔 创建提醒"按钮。

### 3.5 房源对比（阶段 2，1-2 天）

选 2-3 套房源，并排对比关键维度。

**粘合现有代码**：纯前端功能。卡片上加 ☐ 勾选框，选中后底部浮现对比栏，点击展开对比面板。

### 3.6 区域洞察（阶段 2，2-3 天）

用户搜索"未来科技城"时，不只是列表，还看到 AI 生成的区域摘要：

> **未来科技城租房概览（本周）**
> 均价 ¥2,800/月 · 比上月 ↓5% · 43 套在租
> 主要小区：西溪北苑(¥2,200-2,800)、EFC欧美金融城(¥3,500-5,000)、仓溢绿苑(¥1,800-2,500)
> 通勤：到阿里西溪园区骑行 10-15min，地铁 5 号线直达
> 💡 西溪北苑近期有多套转租，价格比市场低 15%，多为阿里员工换工作转租

**实现**：定时任务对所有 listing 按行政区聚合，调 LLM 生成摘要（缓存 24h），搜索时附带返回。LLM 一次生成，多次复用，成本极低。

## 四、平台扩展计划

当前只有豆瓣+闲鱼两个活跃源。扩展策略分三档：

### Tier 1 — 立刻能做（1-2 周）

| 平台 | 方式 | 预估日增量 | 风险 |
|------|------|:--------:|:----:|
| **百度贴吧**（杭州租房吧、杭州转租吧） | Firecrawl，SSR 论坛结构，同豆瓣模式 | 30-50 | 低 |
| **微博超话**（#杭州租房#） | Firecrawl + 搜索 API，内容公开 | 50-80 | 低 |
| **19楼**（19lou.com 杭州租房版） | Firecrawl，SSR 本地论坛 | 20-40 | 低 |

三个平台都是 SSR 的论坛/列表结构，完全复用现有 `crawl_douban_group()` 模式：

```python
# 新增 firecrawl_client.py 中复制豆瓣模式
TIEBA_URLS = ["https://tieba.baidu.com/f?kw=杭州租房", ...]
WEIBO_TOPICS = ["https://s.weibo.com/topic?q=杭州租房", ...]
LOCAL_FORUMS = ["https://hangzhou.19lou.com/forum-1462-1.html", ...]
```

**粘合**：Firecrawl 统一入口，`pipeline.py:fetch_new_listings()` 加三个爬虫调用。LLM 提取 prompt 不变（租房帖的结构化信息是一样的）。

### Tier 2 — 需要一点技巧（2-4 周）

| 平台 | 方式 | 说明 |
|------|------|------|
| **小红书** | 搜索页公开内容 | 不做用户主页爬取，只抓搜索结果页（`xhslink.com` 短链解析），频率控制在 1 req/min。风险可控。 |
| **58同城** | 降级策略 | 当前 PC/移动版均反爬，尝试从百度快照或小程序 API 间接获取。**不投入核心精力**——这个平台已有明确反爬，优先级低于 Tier 1。 |

### Tier 3 — 用户参与（长期）

- **"提交房源"入口**：用户看到好房源可以提交链接，系统自动抓取+提取。UGC 模式补充爬虫盲区。
- **微信群/朋友圈转发**：用户转发租房帖到小程序，自动识别结构化信息。

## 六、关键产品决策

### 6.1 LLM 成本可控

全部 LLM 功能用同一个 DeepSeek V4 Flash：
- 提取（已有）：1000 tokens/条 × 50条/天 ≈ 50K tokens
- 质量评分：200 tokens/条 × 50条/天 ≈ 10K tokens
- 区域洞察：500 tokens × 5 个区域 × 每天一次 ≈ 2.5K tokens
- 自然语言解析：100 tokens/次 × 100次/天 ≈ 10K tokens

日均约 7.2万 tokens。DeepSeek V4 Flash 定价 ¥1/百万 tokens。**日均成本 < ¥0.10**。

### 6.2 不做的事

- **不做用户系统**：MVP 不搞注册登录。收藏用 localStorage，提醒用邮箱（用户自己填）。
- **不做移动 App**：响应式单页适配手机即可。租房大多在电脑上看地图。
- **不做 AI 对话**：不需要 chatbot。LLM 在后台静默工作，用户看到的是结果。
- **不做 58/贝壳**：前一个反爬已死，后一个有法律判例。

### 6.3 关于 LLM 的定位

> **LLM 不是卖点，是引擎。** 用户不知道也不关心背后有没有 AI。他们只关心"找到的房子好不好、真不真、划不划算"。LLM 应该像搜索引擎的 PageRank——在后台默默算分，前台只展示结果。

产品里不提"AI 驱动"、"智能匹配"这类词。用户看到的是：
- ⭐ 质量分（背后是 LLM 多维度评估）
- 💡 区域均价参考（背后是 LLM 聚合总结）
- 🔗 同一房源跨平台（背后是 LLM 去重）
- 搜索"阿里附近 2500 一居"能搜出结果（背后是 LLM 解析）

## 七、总结

现有代码的管线是正确的。问题不在技术，在产品形态。核心改变只有三个：

1. **从搜索框变成地图** — 地图是租房的主交互，搜索框是辅助
2. **从展示字段变成理解房源** — LLM 帮忙判断值不值、真不真、划不划算
3. **从一次性工具变成持续服务** — 收藏+提醒让用户回来

三个新增平台（贴吧、微博、19楼）都是低风险 SSR 抓取，完全复用现有模式。阶段 1 做到地图+质量分+自然语言搜索，产品体验就拉开与豆瓣小组搜索的差距了。
